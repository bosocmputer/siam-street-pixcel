## 1. Engine comparison for a headless AI agent (build, run, test, screenshot; text files; mobile web; quality ceiling; license)

### Takeaway
Only the JavaScript engines (three.js, Babylon.js, PlayCanvas engine-only) can be fully built, run, tested and screenshotted by a headless agent in this container today, with all project files as plain text and a shareable web link. Godot is text-friendly but its web export is limited to the Compatibility renderer and has a track record of iOS-browser crashes; Unity and Unreal both need a running desktop editor (their MCP servers drive a live editor) and Unreal has no web target, so they are poor fits for "Claude builds everything, creator plays on phone via link".

### Inferences
- **Headless build/run/test/screenshot matrix (inferred from the facts above plus the container check):**
  - three.js / Babylon.js / PlayCanvas engine-only (npm + Vite): YES on all four. Text-only TypeScript; runs in headless Chromium with SwiftShader software WebGL (this is exactly how the current project's Playwright e2e works); deploys as static files = shareable link today. Visual verification is limited to software-rendered screenshots (slow, no real GPU timing).
  - PlayCanvas Editor workflow: NO for the agent alone — the Editor is a cloud web app that must be open in Chrome and connected to the local MCP server; scene data lives in the PlayCanvas cloud, not as git text files.
  - Godot 4: PARTIAL. `.tscn`/`.gd`/`.tres` are text and `--headless` export works in CI, but Godot is not installed here (needs a ~100 MB binary download), headless mode uses a dummy renderer so it cannot produce real screenshots without a GPU/virtual display (the web export could still be screenshotted in headless Chromium). Mobile web is the weakest point: Compatibility renderer only, and a history of iOS crashes.
  - Unity: NO. Editor is needed (MCP bridges run inside it); Linux editor + license activation in a no-display container is not realistic for this setup; scenes/prefabs are YAML text but large and GUID-linked; requires the creator's PC running the Editor.
  - Unreal: NO. Binary `.uasset`/`.umap`, Windows-centric editor, tens of GB, no web export (requires Pixel Streaming = paid cloud GPU servers), out of scope for "shareable link on a phone".
- **Quality ceiling**: The visual gap ("looks amateur") is mostly assets + lighting + post-processing, not the engine. three.js and Babylon both have PBR, shadow maps, IBL, bloom/SSAO/tone-mapping (pmndrs `postprocessing`; Babylon built-in pipelines), physics (Rapier / Havok-for-Babylon) and navmesh. Babylon 9 ships more built-in (clustered lights, volumetrics, retargeting, inspector) — fewer libraries for the agent to glue together. Unity/Unreal have a far higher ceiling but it is unusable in this workflow.
- **Recommended direction**: stay on the web/TypeScript stack (three.js upgraded to ~r186, or a migration to Babylon.js 9 if built-in retargeting/geospatial/inspector are worth a rewrite). Move app-store delivery later via a WebView/Capacitor wrapper, which keeps one codebase.
- Migration cost: the existing `rpg-core` is engine-agnostic pure TS, so only the `apps/citywalk` rendering layer would change if switching to Babylon.

## 2. MCP servers for engines and Blender in 2026: local vs remote, maturity

### Takeaway
Every engine/Blender MCP server found is **local-only**: a small Node/Python server on the same machine bridges via localhost (WebSocket/TCP) to a **running editor GUI**. None can be used from Claude Code in a cloud container without the creator's own PC running the editor and the MCP server, so for this project they are not a substitute for a text-and-CLI workflow (Blender in `--background` Python mode is the one usable exception, without MCP).

### Cited Findings
- **Unity (community) CoderGamester/mcp-unity**: ~2.0k stars, 248 forks, MIT, v1.5.0. Unity side runs a WebSocket server inside the Editor (`ws://localhost:8090/McpUnity`), started from Tools > MCP Unity; a local Node server connects to it. Batch mode disabled by default but a headless Editor can opt in. Tools: scenes, GameObjects, components, prefabs, materials, `run_tests`, `get_console_logs`, `set_play_mode_status`, `recompile_scripts`, `batch_execute`. — [github.com/CoderGamester/mcp-unity](https://github.com/CoderGamester/mcp-unity)
- **Unity (official)**: MCP in the AI Assistant package, open beta (announced May 2026), Unity 6+, Cloud-connected project, active subscription or trial; supports Claude Code, Cursor, Windsurf, Claude Desktop, VS Code Copilot; inspects scenes, reads console, edits scripts, triggers editor actions. — [Unity blog](https://unity.com/blog/unity-ai-mcp-how-to-get-started)
- **Unreal (community) chongdashu/unreal-mcp**: ~2.1k stars, MIT, explicitly "EXPERIMENTAL", breaking changes possible, not for production; UE 5.5+; C++ plugin runs a TCP server (port 55557) inside the editor, Python FastMCP server bridges it; build steps assume Visual Studio. — [github.com/chongdashu/unreal-mcp](https://github.com/chongdashu/unreal-mcp)
- **Unreal (official)**: experimental MCP plugin in UE 5.8 running a local server inside the editor. — [gamedev.net](https://gamedev.net/news/4002/); [Sorceress blog](https://sorceress.games/blog/steer-the-best-ai-for-unreal-engine-blueprint-path-2026)
- **Godot Coding-Solo/godot-mcp**: ~6.2k stars, MIT, Node ≥18; wraps the Godot CLI (launch editor, run project, capture debug output, create scene, add node, load sprite, export mesh library, UID management for 4.4+); 14 tools. npm `@coding-solo/godot-mcp` last published 0.1.1 on 3 Feb 2026. A comparison lists it as no live-game control; "Godot MCP Runtime" (Erodenn) offers deeper runtime control. — [github.com/Coding-Solo/godot-mcp](https://github.com/Coding-Solo/godot-mcp); [npm](https://www.npmjs.com/package/@coding-solo/godot-mcp) (`npm view`); [Godot MCP Runtime (Glama)](https://glama.ai/mcp/servers/@Erodenn/godot-mcp-runtime)
- **PlayCanvas playcanvas/editor-mcp-server (official)**: 149 stars, MIT, npm `@playcanvas/editor-mcp-server` 0.7.1 (9 Sep 2026); Node ≥22.18; launched with `npx`, listens on `127.0.0.1:52000`; works only while the Editor is open in Chrome and the user clicks MCP > CONNECT; one Editor at a time; ~130 tools in 15 categories (Entity, Scripts, Assets, Animation, Scene, Viewport, Builds, Store, Runtime, VCS...), ~43k tokens of tool definitions. Older listings describe a Chrome extension (now outdated: client is built into the Editor). — [github.com/playcanvas/editor-mcp-server](https://github.com/playcanvas/editor-mcp-server); [PlayCanvas manual: MCP server](https://developer.playcanvas.com/user-manual/editor/mcp-server/); [llmbase listing](https://llmbase.ai/mcp-servers/play-canvas)
- **Blender ahujasid/blender-mcp**: ~31.8k stars, 3.0k forks, MIT. Blender addon runs an unauthenticated TCP socket server on localhost:9876 inside a running Blender; tools: `execute_blender_code` (arbitrary Python), `look` (renders viewport/camera views), `get_scene_info`, `generate_3d` (Tripo, Hunyuan3D, Hyper3D Rodin, Meshy), `search_assets`/`import_asset` from Poly Haven (CC0, no key), Sketchfab, Poly Pizza. — [github.com/ahujasid/blender-mcp](https://github.com/ahujasid/blender-mcp)

### Inferences
- All of these are stdio/localhost bridges to a GUI editor; in a cloud container without display/GPU they only work if the editor itself can run headless. Blender can run `blender --background --python script.py` on CPU (Cycles/EEVEE-less), which gives the agent most of what blender-mcp offers (scripted modelling, glTF export, rendered previews via Cycles CPU) without MCP — but Blender must be installed first (not present now).
- For the creator (no programming background), any MCP route that needs "keep Unity/Unreal/Blender open on your PC" adds a fragile manual step; the PlayCanvas route needs the creator (or agent) to keep a Chrome tab open with the Editor.
- Maturity ranking by evidence: Blender MCP (very popular, but runs arbitrary code over an open socket) > Godot MCP (popular, CLI-based, but npm package barely versioned) > Unity official (beta) ≈ mcp-unity > PlayCanvas official (young, small user base, but official and frequent releases) > Unreal (experimental).

### Gaps
- Last-commit dates for mcp-unity, unreal-mcp, godot-mcp, blender-mcp could not be read (GitHub API blocked, page did not show dates).
- No evidence found of any remote/hosted (non-localhost) engine MCP service usable from a cloud agent.
- Whether Unity's official MCP works with a batch-mode/headless Linux Editor not documented in sources found.

## 3. Making the real-city map (Chiang Mai) look good: options, licenses, costs

### Takeaway
Google Photorealistic 3D Tiles give the best look instantly and stream into three.js via NASA-AMMOS `3d-tiles-renderer`, but they are streaming-only (no caching/offline/export into the game), require Google attribution, cost $6 per 1,000 root-tile sessions after 1,000 free/month, Chiang Mai coverage is unconfirmed, and the photogrammetry mesh is a single "melted" surface (no per-building collision or gameplay semantics). The game-friendly path is improving OSM procedural buildings (textured facades, roof shapes, props) via OSM2World/Blosm-style generation or in-house code, optionally with Google tiles only as a distant backdrop.

### Cited Findings
- **Google Photorealistic 3D Tiles pricing**: Enterprise SKU "Map Tiles API: Photorealistic 3D Tiles", 1,000 free root-tile requests/month, then $6.00 per 1,000 (up to 100k), tiers $5.10 / $4.20 / $3.30 / $2.40 per 1,000 at higher volumes. — [Google Maps Platform core services pricing list](https://developers.google.com/maps/billing-and-pricing/pricing)
- Billing is per root-tile request; individual tile fetches are not counted against daily quota; one root request covers a session up to ~3 hours (third-party). The old $200 monthly credit ended 28 Feb 2025. — [Map Tiles API usage and billing](https://developers.google.com/maps/documentation/tile/usage-and-billing); [Mantle comparison](https://mantle.place/compare/google-photorealistic-3d-tiles); [afi.io blog](https://blog.afi.io/blog/what-is-the-google-photorealistic-3d-tiles-api/)
- One developer estimated ~$2,440 for 500,000 views/month (2023, old pricing — treat as illustrative). — [Cesium forum: Google 3D Tiles cost](https://community.cesium.com/t/google-3d-tiles-cost/27625)
- **Policies**: Map Tiles API should be used for map visualization; must not pre-fetch, index, store or cache content except under limited terms; offline use, geodata extraction, object detection listed as prohibited non-visualization uses; must use a 3D Tiles renderer that displays copyright attribution and show the Google logo. Photorealistic 3D Tiles are unavailable to EEA-billed projects (403). — [Map Tiles API Policies](https://developers.google.com/maps/documentation/tile/policies); [Map Tiles EEA adjustments](https://developers.google.com/maps/comms/eea/map-tiles)
- Programmatically reading measurements (heights, distances) from Google 3D imagery is "derivative and prohibited". — [Google Maps Platform blog: FAQ on Photorealistic 3D Tiles](https://mapsplatform.google.com/resources/blog/commonly-asked-questions-about-our-recently-launched-photorealistic-3d-tiles/)
- Third-party summary: streaming through a renderer with attribution is allowed, exporting the mesh into a shipped project is not. Cesium forum user: caching tiles offline violates Google's terms. — [Mantle](https://mantle.place/compare/google-photorealistic-3d-tiles); [Cesium forum caching thread](https://community.cesium.com/t/google-map-api-tiles-caching-or-download-not-every-time/26719)

- **Mapbox**: GL JS v3 Standard style adds 3D landmark models and building/terrain shadows; pricing: first 50,000 monthly map loads free, then $5.00/1,000; a load = each Map object init, max 12 h session. `mapbox-gl` 3.33.0 is under a proprietary license ("SEE LICENSE IN LICENSE.txt"); MapLibre GL 6.15.0 is BSD-3-Clause. — [Mapbox pricing](https://www.mapbox.com/pricing); [Mapbox GL JS pricing guide](https://docs.mapbox.com/mapbox-gl-js/guides/pricing.md); [Mapbox v3 migration guide](https://docs.mapbox.com/mapbox-gl-js/guides/migrate.md); [npm registry](https://www.npmjs.com/package/maplibre-gl) (`npm view`)

### Inferences
- Google tiles conflict with CLAUDE.md's "pixel 3D" art direction (a photoreal mesh pixelated will look like mush) and with gameplay needs (collision, navmesh, per-building identity). Policy also forbids offline use, so the game would break without network and every player session costs money after 1,000/month. Best used, if at all, as a far-distance skyline or a separate "real view" mode.
- Most practical upgrade for this project: keep OSM as the source of truth (ODbL — attribution "© OpenStreetMap contributors" required) and generate richer buildings in code or in a build-time pipeline: roof shapes from `roof:shape`, facade textures/atlases per building type (shophouse, temple-excluded per CLAUDE.md rules, condo), window grids, ground-floor shopfronts, street props, trees. OSM2World (Java CLI, headless-friendly) can produce .glb with textures at build time; Blosm needs Blender (and Pro for textures).
- A hybrid "hand-authored hero areas" approach (Tha Phae Gate plaza modelled properly) + procedural rest of city is what most real-city games do; that pattern fits the existing per-zone design.

## 4. Animation retargeting (Mixamo/mocap onto GLB) in three.js and Babylon.js

### Takeaway
three.js has `SkeletonUtils.retargetClip` + `AnimationMixer` (crossfades/blending are mature), but retargeting itself is under-documented and fragile with Mixamo rigs; most teams pre-retarget in Blender or use identical rigs. Babylon.js 9 added first-class retargeting (`AnimatorAvatar.retargetAnimationGroup`, with an interactive tool) that is newer and still fixing bugs (use ≥ 9.7).

### Cited Findings
- three.js: developers report `retarget()`/`retargetClip()` producing bad results even between identical Mixamo YBot rigs; models rotating about X; inverted feet/backward hands with `mixamorig` skeletons; a maintainer suggested rewriting the example around glTF and completing SkeletonUtils docs. — [three.js forum: Fixing SkeletonUtils retarget/retargetClip](https://discourse.threejs.org/t/fixing-skeletonutils-retarget-and-retargetclip-functions/65149/2); [three.js forum: mixamorig inverted feet](https://discourse.threejs.org/t/skeletonutils-retarget-doesnt-work-with-mixamorig-skeleton-inverted-feet-backward-hands/54892); [three.js forum: retargeting rotates model](https://discourse.threejs.org/t/retargeting-animation-sometimes-rotates-model/25394)
- Mixamo→VRM mapping needs a custom bone map; VRM 0.x characters stood backwards, VRM 1.0 correct. — [three.js forum: Fixing SkeletonUtils thread](https://discourse.threejs.org/t/fixing-skeletonutils-retarget-and-retargetclip-functions/65149/7)
- Babylon.js 9.0 introduced animation retargeting with an interactive tool that exports a code snippet; API `AnimatorAvatar.retargetAnimationGroup()` with options incl. root-position fixes. — [Babylon forum: Introducing Animation Retargeting](https://forum.babylonjs.com/t/introducing-animation-retargeting/62547); [animatorAvatar.d.ts @babylonjs/core 9.18.0](https://app.unpkg.com/@babylonjs/core@9.18.0/files/Animations/animatorAvatar.d.ts)
- Babylon bug: retargeting could stop a playing clip and snap to rest pose; fixed in PR #18450, use 9.7.0+; recommended to retarget once at load and cache. Mixamo clips gave root rotation offset/crossed hands because Mixamo uses hips as root; rest poses must closely match. — [Babylon forum: snaps to rest pose](https://forum.babylonjs.com/t/after-anim-retarget-stopping-current-animation-jumps-to-rest-pose/63379); [Babylon forum: rotated incorrectly, hands misaligned](https://forum.babylonjs.com/t/retargeted-animation-is-rotated-incorrectly-and-has-hands-misaligned/63218); [Babylon forum: how to properly retarget](https://forum.babylonjs.com/t/how-to-properly-retarget-animations/63568/6)
- Babylon: Mixamo clips can be mapped onto Ready Player Me avatars by matching `mixamorig:`-prefixed bone names without Blender. — [Babylon forum: Mixamo to RPM](https://forum.babylonjs.com/t/apply-mixamo-animation-to-ready-player-me-avatar-without-passing-character-through-blender-mixamo/46054/4)

### Inferences
- The project already has a `joints`/`restFix` mapping layer in assets.json (per CLAUDE.md), which is the same idea forum users converge on (bone map + rest-pose correction); hand-keyed clips in `src/anim/clips.ts` look amateur mainly because they are hand-keyed, not because of the engine.
- Lowest-risk path: pick one canonical humanoid rig (e.g. Mixamo/Humanoid naming), retarget mocap clips offline (Blender `--background` script or a Node glTF-transform script) into that rig, ship baked clips in .glb, and use `AnimationMixer` for blending at runtime. Root motion: neither three.js nor Babylon has built-in root-motion extraction in sources found; it is typically done by stripping the hips/root translation track and applying it to the character controller in code.
- Mixamo licensing (Adobe account needed; animations royalty-free for games) not verified this session.

### Gaps
- No official three.js docs/examples for glTF-based retargeting found; root-motion support specifics for both engines not found in sources.
- Mixamo's 2026 availability/terms not checked.

## 5. Real AI-built ("vibe-coded") 3D web games that reached players (2025–2026) and their stack

### Takeaway
The flagship case is Pieter Levels' fly.pieter.com flight sim (Feb 2025), built with Cursor + Claude + three.js, which reached tens of thousands of concurrent players and real (self-reported) revenue; the yearly Vibe Jam (≥90% AI-written code, three.js recommended) shows three.js is the de facto stack for AI-built browser 3D games. Revenue figures are self-reported and inconsistent.

### Cited Findings
- Levels built a multiplayer flight sim in ~3 hours (Feb 2025) with Cursor, Claude and Three.js, having never shipped a game; reported $12K MRR as of May 2025. — [Indie Hackers](https://www.indiehackers.com/post/2NUIOp80SUWuPmmfKoS9)
- Other reports: ~$138K/month by Nov 2025 and peak 22–26K simultaneous players, 320K users in first month; revenue from in-game ad blimps (~$5K/month each) and $29.99 plane skins. Ziva (Apr 2026) says ">$50K/month"; figures conflict and are self-reported. — [Sorceress: Real vibe coding apps 2026](https://sorceress.games/blog/real-vibe-coding-apps-what-indies-built-in-2026); [Ziva: vibe coding games](https://ziva.sh/blogs/vibe-coding-games)
- Ziva cites Nicolas Zullo getting 45,000 players with zero human-written code. — [Ziva](https://ziva.sh/blogs/vibe-coding-games)
- Cursor Vibe Jam 2026: ≥90% of code must be AI-written; three.js recommended but any engine allowed; prizes $25K/$10K/$5K; ~945 games submitted, >242,000 players; 1 in 7 multiplayer entries used Colyseus. Winners listed as TBA in sources found. — [vibej.am/2026](https://vibej.am/2026/); [SummerEngine guide](https://www.summerengine.com/blog/cursor-vibe-jam-2026-guide); [Colyseus blog](https://colyseus.io/blog/vibe-jam-2026/)

### Inferences
- These successes are mostly simple, stylized, short-session games (flight, arcade) — not content-heavy action RPGs with character animation; they validate three.js + AI for reach and shareable links, but not for "AAA-looking" results. Visual quality in these hits comes from a coherent simple art style, which supports keeping the pixel-3D direction rather than chasing photorealism.
