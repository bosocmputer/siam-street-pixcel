## 1. การเปลี่ยนที่สำคัญ

เกมเปลี่ยนเป็น real-time action จึงต้องมี simulation ระหว่างต่อสู้ การใช้ HTTP polling ตามแนว v2 ไม่ใช่ทางเลือกสำหรับการเคลื่อนที่ หลบ และตัดสินความเสียหายร่วมกัน

แยกสองส่วน: ห้องต่อสู้มี state ที่เปลี่ยนเร็วและเซิร์ฟเวอร์ตัดสิน ส่วนโลกแคมเปญและความก้าวหน้าคงอยู่ในฐานข้อมูล ไม่ให้ทุกพื้นที่ของประเทศไทยอยู่ใน simulation เดียวตลอดเวลา

สมมติทำงานด้วยผู้สร้างกับ coding agent หรือทีมเล็ก งบและเครื่องเป้าหมายยังไม่มีตัวเลขยืนยัน การเลือกเครื่องมือยังกลับได้หลังทดลองหนึ่งฉาก

## 2. Stack สำหรับพิสูจน์แนวคิด

| ส่วน | ข้อเสนอ | เหตุผล/สิ่งที่ต้องตรวจ |
|---|---|---|
| Combat client | Phaser + TypeScript + Vite | Phaser เป็น framework 2D สำหรับเว็บ [S1]; ต้องวัด input และ frame time บนมือถือจริง |
| เมนู/แผนที่ | React + MapLibre GL JS | ใช้กับบัญชี ปาร์ตี้ และแผนที่ แยกจากฉากต่อสู้ ลด renderer ที่ทำงานพร้อมกัน |
| Multiplayer | Node.js + TypeScript + Colyseus | ห้องและ authoritative state sync [S2]; ตั้งเป้าทดสอบสองคนก่อน ไม่อ้างว่ารองรับ MMO แล้ว |
| Simulation | โมดูล TypeScript ฝั่งเซิร์ฟเวอร์ | ตัดสินตำแหน่ง hit, cooldown, health และ encounter completion; ต้องทำตรรกะชนที่ใช้ร่วมได้ ไม่สมมติว่า Phaser physics รันบนเซิร์ฟเวอร์ได้ทันที |
| Persistent state | PostgreSQL; PostGIS เมื่อเริ่มใช้ geometry จริง | แคมเปญ พลังที่ปลดล็อก รางวัล และเวอร์ชันพื้นที่; ขั้น A ใช้ fixture ได้ |
| Account | Supabase Auth เป็นตัวเลือกสำหรับขั้น B | ต้องพิสูจน์การตรวจ token ที่ server และสิทธิ์เข้าปาร์ตี้/แคมเปญ; ขั้น A ไม่มีบัญชีจริง |
| Assets | Sprite/เสียงที่มีสิทธิ์ + object storage/CDN เมื่อเผยแพร่ | ขั้น A ใช้รูปทรงอ่านง่ายก่อน ไม่ผูกการทดสอบความสนุกกับ pipeline 3D |
| Basemap | แหล่ง tiles ที่มีสิทธิ์เผยแพร่ | MapLibre เป็น renderer ต้องจัดหา tiles/style/fonts แยก ไม่เท่ากับมีแผนที่ให้ใช้ฟรีไม่จำกัด |

ไม่ล็อก exact versions ก่อนทำ compatibility spike และ lockfile ตัวเลือกอย่าง Godot/native ทบทวนเมื่อผลวัดแสดงว่า browser เป็นข้อจำกัดต่อการเล่นจริง ไม่เพิ่ม engine สองชุดในต้นแบบเดียว

## 3. ขอบเขตข้อมูล

- `campaign`: โลกของกลุ่มเพื่อนและสมาชิกที่มีสิทธิ์ ไม่มีการอ้างว่าเป็นเจ้าของพื้นที่จริง
- `area`: stable ID ของพื้นที่อ้างอิง พร้อมชื่อ แหล่งข้อมูล และ template ฉากสมมติ
- `area_revision`: กฎหนึ่งช่อง เส้นทางที่เปิด ผู้มีส่วนร่วม และ version ของเนื้อหา
- `power_definition`: กติกาที่ผู้พัฒนาอนุมัติเท่านั้น ไม่มีโค้ดจากผู้เล่นหรือ LLM เข้า simulation
- `encounter`: room ID, seed, area revision ตอนเริ่ม, loadout และ roster ที่ server ยืนยัน
- `completion`: ผลจบรอบที่รับรองจาก server ใช้ ID เดิมเมื่อ retry
- `reward_ledger`: รางวัลของแต่ละคน ผูก completion และ recipient เพื่อป้องกันรับซ้ำ
- `rewrite_proposal`: ตัวเลือกเปลี่ยนกฎ ผู้ที่ต้องยืนยัน และ revision ที่ใช้เสนอ

การโจมตีหนึ่งครั้งไม่เขียนฐานข้อมูลทีละเฟรม เก็บ state การต่อสู้ในห้องและบันทึกเฉพาะ boundary ที่จำเป็น เช่นผลจบรอบ การเขียนโลกไม่เปลี่ยน state ของห้องที่เริ่มไปแล้ว

## 4. Flow ที่ต้องรักษาความถูกต้อง

1. Server ตรวจสิทธิ์สมาชิกและ loadout แล้วตรึง snapshot โลกสำหรับห้อง
2. Client ส่ง input พร้อม sequence; server ตรวจอัตราส่ง การเคลื่อนที่ cooldown และผลโจมตี
3. Client ทำการแสดงผลให้ลื่นได้ แต่ไม่ส่งคำสั่งเพิ่มเลือด/ของ/ชัยชนะเป็นข้อเท็จจริง
4. เมื่อชนะ server บันทึก completion และรางวัลอย่าง idempotent ด้วย transaction ไม่พึ่ง browser หน้าจอชัยชนะ
5. ทีมเลือกกฎและยืนยันร่วมกัน หากสมาชิกไม่ครบหรือปฏิเสธ รางวัลคงอยู่และไม่เปลี่ยนพื้นที่
6. Commit กฎใช้ expected revision ถ้าพื้นที่เปลี่ยนแล้วต้องแสดงผลใหม่ให้ทีมยืนยันอีกครั้ง ไม่ใช้ last-write-wins เงียบ ๆ

มีสิทธิ์อ่านประวัติและเขียนกฎตาม campaign; การรู้ room ID อย่างเดียวไม่ให้สิทธิ์แก้โลก ปิดรับ input หลัง completion เพื่อป้องกันผลซ้ำ

## 5. เน็ตหลุดและเหตุขัดข้อง

- หลุดชั่วคราว: ทดลอง grace period ที่กำหนดค่าได้และ reconnect เข้าห้องเดิม ต้องทดสอบผลต่อการรับความเสียหายให้ชัดก่อนเปิดเกม
- Server ตายก่อนจบ: รุ่นทดลองยอมเริ่มรอบใหม่โดยไม่หักของถาวร แจ้งความล้มเหลวตรง ๆ ไม่ปลอมผลชนะ
- Server จบแล้วแต่ UI ยังไม่เห็น: อ่าน completion เดิมกลับมาได้ ไม่แจกใหม่
- ฐานข้อมูลไม่พร้อม: แสดงสถานะกำลังยืนยันผล ไม่ประกาศว่ารางวัลบันทึกสำเร็จ การ retry ใช้ ID เดิม
- เนื้อหาเปลี่ยนเวอร์ชัน: ห้องที่เริ่มไปใช้เวอร์ชันเดิม การปิดรองรับเวอร์ชันต้องรอห้องจบหรือมีข้อความจบรอบที่ออกแบบไว้

มาตรวัดที่ต้องเห็นในการทดลอง: frame time, latency/jitter, reconnect, invalid inputs, room crash และ reward commit failure ไม่มีข้อมูลพิกัดจริงของผู้เล่นใน log

## 6. การส่งกฎข้ามพื้นที่

ต้นแบบใช้กราฟพื้นที่สองจุดและเส้นเชื่อมหนึ่งเส้นที่นิยามไว้ เส้นเกมไม่ได้อ้างการจราจรหรือเส้นทางเดินจริง การขยายภูมิศาสตร์ต้องมี source/version ของ boundary และ adjacency ที่ตรวจแล้ว

กฎข้ามเขตได้หนึ่ง hop และไม่ stack กับกฎพื้นที่อีกชุด เลือกกฎที่จะใช้ก่อนเริ่มห้อง ผลของเส้นทางจึงทดสอบซ้ำได้โดยไม่ทำ simulation โลกทั้งประเทศ

ทุกพื้นที่มีฉากตั้งต้นแม้ไม่มี POI จริง แยกพิกัดสถานที่อ้างอิงกับตำแหน่งผู้เล่นอย่างชัดเจน ไม่ขอ GPS ในต้นแบบ ต้องตรวจ attribution และเงื่อนไขของชุดแผนที่ที่เลือกก่อนเผยแพร่

## 7. ลำดับพิสูจน์และการตรวจที่ต้องทำเมื่อเริ่มเขียนเกม

| ขั้น | สิ่งที่ส่งมอบ | หลักฐานที่ใช้ตัดสิน |
|---|---|---|
| A | Single-player graybox บอสหนึ่งตัว พลังแช่แข็ง/สะท้อน | คนเล่นใช้ฉากได้เองและอยากเล่นรอบสอง |
| B | ห้องสองคน server-authoritative และสองพื้นที่ที่ฝากกฎได้ | ใช้สองเครื่องจริง ทดสอบเน็ตหลุด ส่งคำสั่งซ้ำ และเปลี่ยน revision ชนกัน |
| C | ความก้าวหน้าถาวรและ playtest ตาม GDD | ตรวจรางวัลไม่ซ้ำ ลำดับปลดล็อก และพฤติกรรมกลับมาเล่น |

เป้าหมายคุณภาพทดลอง ไม่ใช่ผล benchmark: เครื่องกลางที่เลือกทดสอบควรรักษาอย่างน้อย 30 FPS ในฉากบอส และการทดลอง latency 50/100/200 ms ต้องบันทึกความรู้สึกหลบกับอาการ correction ไม่ใช้ค่าเฉลี่ย FPS อย่างเดียว ต้องรายงานรุ่นเครื่อง browser จำนวน entities และเครือข่ายทุกครั้ง

การทดสอบ logic ที่จำเป็นเมื่อมีโค้ด: กฎสองแบบไม่ปิดทางผ่าน, server ปฏิเสธ cooldown ผิด, completion ซ้ำไม่เพิ่มรางวัล, สมาชิกนอกกลุ่ม commit ไม่ได้, revision เก่าต้องยืนยันใหม่ และ reconnect ไม่สร้างผู้เล่นซ้ำ

ยังไม่กำหนด CCU หรือค่าใช้จ่ายรายเดือนจนวัด room cost และทราบจำนวนผู้เล่นพร้อมกันที่ต้องรองรับ

## 8. เทคนิค AI ที่มีประโยชน์ตามลำดับ

ช่วยเขียนเครื่องมือทดสอบและสร้าง variation จาก schema ที่ตรวจได้ก่อน ใช้ AI ทำภาพทดลองได้เมื่อจำเป็นแต่ตรวจสิทธิ์และความสม่ำเสมอของ style หากต้องใช้ Blender pipeline ให้ทดลอง asset หนึ่งตัวจน export เข้าเกมจริงสำเร็จ ไม่เอาคำบอกเล่าเรื่องโมเดลในกลุ่มมาเป็นข้อกำหนด production

AI ไม่ตัดสิน hit, รางวัล, สิทธิ์พื้นที่ หรือสร้างกฎสดของแมตช์ ความสนุกหลักต้องยังทำงานเมื่อไม่มีบริการ AI ออนไลน์
