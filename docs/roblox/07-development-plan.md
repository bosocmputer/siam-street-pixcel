# 07 — แผนพัฒนาและเกณฑ์ส่งมอบ

[สารบัญ](README.md) · [สถาปัตยกรรม](06-roblox-architecture.md) · [สถานะจริง](../coordination/STATUS.md)

เอกสารนี้เป็น roadmap เสนอ ไม่ใช่ผลดำเนินงานหรือกำหนดส่งที่รับรอง ยังไม่ประเมินชั่วโมงรวมเพราะไม่มี baseline การผลิต asset และยังไม่พิสูจน์การเชื่อม Studio บนเครื่องนี้

## 1. หลักการทำงาน

ทำทีละ slice ที่เล่นหรือพิสูจน์ได้ อย่าเริ่มจากระบบ MMORPG ทุกอย่างพร้อมกัน งานภาพใช้ graybox จนจังหวะต่อสู้ผ่าน เมื่อจุดหนึ่งไม่ผ่านให้แก้จุดนั้นก่อนขยายแผนที่

การทำเอกสารรอบนี้ไม่เริ่มติดตั้งหรือเขียนเกม ขั้นถัดไปคืออ่าน/ทบทวนแบบและเลือก milestone หากผู้สร้างสั่งเริ่มพัฒนาแล้วให้ทำงานในขอบเขตนั้นต่อได้ ไม่ต้องขออนุญาตซ้ำทุก task

## 3. งานช่วงแรกที่แยกหยิบได้

### R00 — ยืนยัน AI bridge

- **R00-01 ตรวจเครื่องและเปิด Studio:** ระบุเวอร์ชัน ตำแหน่งติดตั้ง และ Place ทดสอบ ผู้สร้าง login เอง; ผ่านเมื่อเปิด Place ได้ ไม่บันทึกรหัสผ่าน
- **R00-02 เชื่อม MCP:** เลือก session ให้ถูก อ่านต้นไม้ฉากได้; ผ่านเมื่อเก็บ tool result จริง ไม่ใช้ภาพ setting เพียงอย่างเดียว
- **R00-03 พิสูจน์รอบแก้และทดสอบ:** สร้างวัตถุ/สคริปต์เล็กในพื้นที่ทดสอบ รัน อ่าน console และถ่ายภาพ; ผ่านเมื่อ export/sync กลับ repo และระบุ checkpoint

ไฟล์คาดว่าจะเกี่ยวข้องเมื่อเริ่ม: บันทึก setup ใน `docs/coordination/`, source ตัวอย่างใน `roblox/`; config MCP เครื่องผู้ใช้ไม่ควรคัดลอก secret ลง Git

### R01 — พื้นฐานฉากและโค้ด

- **R01-01 Source mapping:** สร้างโครง shared/server/client และเลือก sync แบบเดียว; ผ่านเมื่อแก้หนึ่งไฟล์แล้วพิสูจน์ใน Studio และอ่านกลับตรงกัน
- **R01-02 Movement/camera:** บุคคลที่สามพร้อมจุดเกิด collision และ mobile layout; ผ่านเมื่อเดินรอบห้อง มุมแคบ และกลับจุดเกิดได้
- **R01-03 Test harness/catalog:** ทำ pure math และ schema checks พร้อมกรณีปกติ/ขอบ; ผ่านเมื่อมีวิธีรันทดสอบจริงที่บันทึกไว้

### R02 — Combat slice

- **R02-01 Basic attack:** หนึ่งสไลม์ หนึ่งคอมโบ server hit; ตรวจโดนครั้งเดียว ระยะ ผนัง ตาย และ respawn
- **R02-02 Defense:** เพิ่มรับ/หลบและ stamina; ตรวจด้านหน้า/หลัง กดรัว ค่าติดลบ และ action ที่ซ้อนกันไม่ได้
- **R02-03 Crescent:** เพิ่มชาร์จ/ปล่อย/cancel; ตรวจหลายเป้า เป้าเดิม ผนัง ข้ามเฟรม ตายกลางชาร์จ และ cleanup
- **R02-04 Feel pass:** ให้คนลองสั้น ๆ สังเกตโดยไม่บอกปุ่มซ้ำ; บันทึกภาพ ปัญหา และความอยากเล่นซ้ำ

แต่ละ task จำกัดการแก้เฉพาะระบบของตน ถ้าเกินประมาณห้าไฟล์ใหญ่ให้แยกย่อยก่อน ไม่ใส่ inventory, guild และแผนที่ทั้งเมืองใน combat task

### R03–R06 — แยกงานก่อนเริ่มแต่ละช่วง

รายการล่วงหน้า: replicated enemy state, party lifecycle, profile lease, reward transaction, quest state machine, craft transaction, encounter budget, map import, art replacement และ load test

ก่อนลงมือในแต่ละช่วง AI ต้องแตก task ย่อยที่มี dependency, files, acceptance และ verify ใน [TASKS](../coordination/TASKS.md) ตามสิ่งที่สร้างจริงแล้ว ไม่ถือว่ารายการภาพรวมนี้เป็นงานที่ทำเสร็จใน session เดียวได้

## 4. Definition of Done ของทุก task

1. ตรง acceptance และไม่เพิ่มขอบเขตนอกงาน
2. source ใน Git ตรงกับ Studio/checkpoint ที่ส่งต่อ
3. ตรวจอย่างเหมาะสม พร้อมคำสั่ง/ขั้นตอนและผลจริง
4. ถ้าแก้สิ่งที่ผู้เล่นเห็น มีภาพหรือบันทึกทดสอบ runtime
5. ไม่มี error ค้างที่ถูกมองข้าม ไม่มี connection/instance เพิ่มโดยไม่ cleanup
6. อัปเดต task, status, worklog และ handoff โดยระบุสิ่งที่ยังไม่ทำ

ถ้าไม่มีเครื่องมือทดสอบให้ระบุ NOT RUN และเหตุผล อย่าเขียน PASS แทนการคาดว่าโค้ดน่าจะใช้ได้

## 5. เกณฑ์ประสิทธิภาพสำหรับตั้งการทดลอง

ทุกค่าด้านล่างเป็นเป้าคุณภาพภายใน ไม่ใช่ผลทดสอบหรือ SLA และยังต้องเลือกเครื่องทดสอบจริงก่อนใช้ตัดสิน

| สถานการณ์                                        | เป้าทดลอง                                                      |
| ------------------------------------------------ | -------------------------------------------------------------- |
| PC เป้าหมาย กลุ่ม 12 คน / ศัตรู active สูงสุด 32 | P95 frame time ไม่เกิน 16.7 ms หลัง warm-up                    |
| มือถือเป้าหมาย โหมดประหยัด สถานการณ์เดียวกัน     | P95 frame time ไม่เกิน 33.3 ms                                 |
| Server ภาระเดียวกัน                              | P95 frame time ไม่เกิน 33.3 ms และคิวงานไม่โตต่อเนื่อง         |
| เดินเข้าออกเซลล์/รอยซ้อน                         | ไม่ตกพื้นหรือได้ผล combat จากฉากที่ยังไม่พร้อม                 |
| Memory หลังเล่นซ้ำและกลับพัก                     | ไม่เพิ่มต่อเนื่องทุก cycle ต้องมีกราฟและวิเคราะห์              |
| Load รอบแรก                                      | เป้าเริ่มควบคุมได้ภายใน 15 วินาทีภายใต้เครือข่ายทดสอบที่บันทึก |

รายงานต้องระบุรุ่นเครื่อง OS graphics quality จำนวน client ผู้เล่นจริง/บอต จำนวนศัตรู RTT รุ่น Place และ commit ใช้ช่วง warm-up อย่างน้อย 2 นาที เก็บอย่างน้อย 15 นาทีต่อ scenario และเก็บ frame time ไม่ใช่ FPS เฉลี่ยอย่างเดียว

ทดสอบเพิ่มคน 1 → 2 → 4 → 8 → 12 ตามทรัพยากรที่มี แยกรันหลาย client ในเครื่องเดียวออกจากเล่นบนหลายเครื่อง การจำลอง NPC นักดาบ 10 ตัวใช้หา CPU/VFX bottleneck ได้ แต่ไม่ใช่หลักฐานรับผู้เล่นจริง 10 คน

ถ้าไม่ผ่าน ให้หา CPU/GPU/replication/asset bottleneck ลดเอฟเฟกต์ งาน AI หรือรายละเอียดที่ไม่ช่วยเล่น แล้ววัดซ้ำ ไม่เปลี่ยนตารางเกณฑ์ให้เขียวโดยไม่บอกผู้สร้าง

## 6. การทดลองความสนุก

ชุดแรกเสนอคนใหม่ 5–8 คน เป็นกลุ่มเล็กสำหรับหาปัญหา ไม่ใช่ผลสำรวจตลาดหรือสถิติความสำเร็จ

| สมมติฐาน         | สิ่งที่ดู                                                 | สัญญาณให้แก้                        |
| ---------------- | --------------------------------------------------------- | ----------------------------------- |
| เริ่มง่าย        | อย่างน้อย 4 ใน 5 คนแรกฟัน หลบ และใช้สกิลได้หลัง tutorial  | ต้องบอกปุ่มซ้ำหรือหลงเมนูหลายคน     |
| ต่อสู้สนุก       | อย่างน้อย 3 ใน 5 สมัครใจลองสู้อีกรอบโดยไม่เสนอรางวัลเพิ่ม | ทุกคนหยุดทันทีหลังรับของ            |
| เมืองมีค่า       | ผู้เล่นบอกจุดจำได้และใช้จุดนั้นนัดเพื่อน                  | แผนที่เป็นทางเดินยาวที่อยากข้ามตลอด |
| เล่นด้วยกันมีค่า | คู่ผู้เล่นช่วยกันและเข้าใจว่าตัวเองช่วยอะไร               | คนหนึ่งทำทั้งหมด อีกคนยืนดู         |
| เนื้อเรื่องพอดี  | ข้ามบทพูดได้แล้วยังไปต่อถูก                               | tutorial หรือเควสต์ขวางการเล่น      |

ถ้าจำนวนผู้ทดสอบต่างจากนี้ให้รายงานตัวเศษ/ตัวส่วนตามจริง ไม่แปลงกลุ่มเล็กเป็นตัวเลข retention ระดับตลาด

## 7. เงื่อนไขก่อนชวนทดสอบ Closed alpha

จบเนื้อเรื่องได้ทั้งเดี่ยวและกลุ่ม, ไม่มีบั๊กทำของซ้ำ/โหลดข้อมูลทับ/เควสต์หลักติดที่รู้แล้วยังไม่แก้, มือถือเป้าหมายอ่านปุ่มและพื้นเตือนได้, asset ownership/สิทธิ์ครบ และผู้สร้างได้เห็น build ที่จะให้คนอื่นลอง

R00–R05 ใช้พื้นที่ทดสอบส่วนตัวก่อน การ publish ที่จำเป็นเพื่อทดสอบบริการต้องระบุว่าเป็น private/test หรือ public และทำในขอบเขตที่ผู้สร้างอนุญาต ไม่เปิดสู่สาธารณะเงียบ ๆ

## 8. สิ่งที่ตัดก่อนถ้างานบาน

ตัดอาชีพเพิ่ม ภายในอาคารตกแต่งเต็ม ระบบ mentor การ์ดแชร์ และทางลับซับซ้อนก่อน รักษาแกนเดิน-สู้-สกิล-เพื่อน-รางวัล-บันทึก ห้ามตัด server validation หรือความถูกต้องของข้อมูลเพื่อให้เปิดได้เร็ว

## 9. ประตูขยายหลัง MVP

เพิ่มอาชีพที่สองเมื่อ combat แกนเดิมผ่าน; ขยายคูเมืองเมื่อเซลล์แรกผลิตซ้ำได้; เพิ่มเมืองที่สองเมื่อ schema เมืองไม่ hardcode เชียงใหม่; เริ่มธุรกิจเมื่อมีคนเล่นกลับและข้อมูลต้นทุนจริง

รายงานการตัดสินใจทุกครั้งเป็น “หลักฐาน → ทางเลือก → ข้อเสนอ → ผู้ตัดสิน” ใน [บันทึกการตัดสินใจ](09-decisions-and-sources.md) แยกสิ่งที่ผู้สร้างตกลงแล้วออกจากสิ่งที่ AI เสนอ
