# 04 — แผนที่จริง การออกแบบเมือง และการขยายโลก

[สารบัญ](README.md) · [แอสเซ็ต](05-art-and-asset-pipeline.md)

## 1. รักษาอะไรจากของจริง

รักษาตำแหน่งสัมพันธ์ แนวถนน จุดตัด ทางเข้าซอย แนวคูน้ำ รูปทรงกำแพง และอาคารเด่นที่มีข้อมูลอ้างอิงเพียงพอ ผู้เล่นควรจำย่านได้โดยไม่ต้องแปะชื่อทุกอาคาร

การใช้งานอาคาร ความสูง หน้าร้าน วัสดุ ภายในอาคาร และรายละเอียดที่ข้อมูลแผนที่ไม่มี ให้ติดสถานะประมาณ/แต่งขึ้น ไม่อ้างว่าเป็น digital twin ที่ตรวจครบหรือโมเดลสแกน

## 2. พื้นที่สามชั้น

| ชั้น                 | ข้อมูล                                    | กฎ gameplay                                   |
| -------------------- | ----------------------------------------- | --------------------------------------------- |
| เมืองฐาน             | ภูมิศาสตร์และโครงข่ายจริง                 | ทางเดิน จุดพัก สมุด และการพบเพื่อน            |
| พื้นที่เล่นที่จัดไว้ | จัดเส้นทางและช่องผ่านบนฐานเดิม            | ต่อสู้เฉพาะเขตที่ออกแบบ ไม่สุ่มมอนทุกหน้าร้าน |
| รอยซ้อน              | ฉากแต่งที่มีทางเข้าอ้างอิงจุดหนึ่งในเมือง | ทำห้องดันเจียน ระยะทางพิเศษ และบอสได้         |

ศาสนสถาน โรงพยาบาล โรงเรียน และพื้นที่อ่อนไหวใช้เป็นฉากสงบ/ขอบเขตห้ามต่อสู้ ไม่ใส่มอนบอสไว้ในอาคารจริงเหล่านั้น พื้นที่อยู่อาศัยไม่เปิดรายละเอียดภายในหรือข้อมูลผู้อยู่อาศัย

## 3. เขตแรกที่เสนอ

MVP เลือกหน้าต่างพื้นที่ประมาณ 300 × 300 เมตรรอบท่าแพและทางเดินติดกัน จุด origin และขอบเขตแน่นอนยังต้องตรวจข้อมูล ไม่ใช่ bbox ที่ดึงสำเร็จแล้วใน Roblox

เส้นทางเนื้อเรื่องประกอบด้วยจุดพัก, ลานฝึกในรอยซ้อน, ตรอกสำรวจ 3 จุด, เสาสะท้อน, ทางเข้าโกดังสมมติ และทางกลับจุดพัก ออกแบบเป็นวงกลับถึงเดิม มีทางตัดหลังผ่าน Q004

โกดังเป็นฉากสมมติ ไม่แทนร้านจริงที่กำลังทำธุรกิจ และไม่อ้างว่ามีสถานที่ลับอยู่ใต้ประตูหรือวัดจริง

### เป้าระยะทางทดลอง

จากจุดเกิดถึงการโจมตีแรกภายใน 60 วินาที; ช่วงเดินที่ไม่มีการตัดสินใจไม่เกินประมาณ 30 วินาที; ระหว่างเป้าเควสต์ควรมีเบาะแสหรือจุดสนใจ ผู้เล่นกดติดตามงานแล้วเห็นทิศ ไม่ถูกบังคับอ่านแผนที่ตลอด

ถ้าเส้นทางจริงเดินแล้วไม่สนุก ให้ปรับความเร็ว เพิ่มจุดพัก/ทางกลับ หรือย้าย gameplay เข้ารอยซ้อนก่อนบิดเส้นถนนหลัก คงทางเดินเมืองที่เป็นข้อมูลจริงไว้ตรวจแยกได้

## 4. แหล่งข้อมูลและสิทธิ์

ใช้ OpenStreetMap เป็นผู้สมัครหลักสำหรับโครงถนน/อาคาร พร้อม snapshot วันที่ OSM IDs และ attribution OSM ระบุให้เครดิตผู้ร่วมทำแผนที่และใช้ ODbL กับฐานข้อมูล; วิธีแจกข้อมูลแปลงต้องตรวจตามรูปแบบใช้งานจริง ไม่เหมารวมว่าทุกไฟล์ภาพหรือโมเดลต้องมีเงื่อนไขเดียวกัน ดู [Copyright and License](https://www.openstreetmap.org/copyright)

ภาพที่ผู้สร้างให้ใช้เทียบองค์ประกอบ ไม่ถือว่าได้สิทธิ์คัดลอกภาพดาวเทียมหรือ texture จากผู้ให้บริการแผนที่ ต้องมีสิทธิ์สำหรับภาพถ่าย โลโก้ และข้อมูลชุดอื่นแยกกัน

ข้อมูลเก่าใน `apps/chiangmai-world/public/data/old-city.json` เป็นผู้สมัครให้ตรวจและนำกลับมาใช้ด้านข้อมูล ไม่ใช่ asset Roblox ที่พร้อมใช้ ต้องตรวจวันที่ ความครอบคลุม เงื่อนไข และผลแปลงอีกครั้ง

ข้อเท็จจริงจาก metadata ในไฟล์ (ตรวจ 2026-10-15): ที่มา OpenStreetMap ใบอนุญาต ODbL-1.0, bbox lat 18.7778–18.8012 / lon 98.974–98.996 (ประมาณ 2.6 × 2.3 กม. ใหญ่กว่าพื้นที่ MVP 300 × 300 ม. มาก), origin 98.985, 18.7895 (ยังไม่ได้ยืนยันว่าตรงท่าแพ), อาคาร 8,808, ถนน 2,034, น้ำ 53, ขนาดไฟล์ราว 2.25 MB และระบุว่าความสูงอาคารและรายละเอียดหน้าตึกเป็นค่าประมาณ ต้องตัดเฉพาะบริเวณท่าแพและเลือก origin ใหม่ก่อนใช้

## 5. Pipeline ข้อมูลสู่เมือง

1. ระบุขอบเขตพื้นที่และรายการสิ่งที่ต้องแม่น
2. เก็บ raw snapshot แบบไม่แก้ทับ พร้อมแหล่งที่มาและใบอนุญาต
3. แปลงพิกัดเป็นระยะท้องถิ่น ตรวจเส้นซ้ำ polygon เสีย และส่วนที่ขาด
4. ทำ graybox ของถนน คูน้ำ ทางเท้า และอาคารก้อนเรียบ
5. เดินสำรวจใน Studio ตรวจจุดตัด ช่องเดิน ความสูง และการชน
6. วาง gameplay layer โดยแยกจากฐานข้อมูลจริง
7. เปลี่ยนก้อน graybox เป็นชุดอาคารและ landmark ที่ตรวจแล้ว
8. ตรวจ streaming, แสง, เงา, การชน และอุปกรณ์จริงก่อนเพิ่มพื้นที่

กรณีข้อมูลหายให้บอก missing feature และวาดเติมเป็น estimated/manual อย่าสร้างถนนสุ่มแล้วติดป้ายว่ามาจากแผนที่จริง

## 6. พิกัด หน่วย และความคลาดเคลื่อน

เก็บ latitude/longitude ต้นฉบับ ใช้ระบบฉายพิกัดท้องถิ่นที่เหมาะกับพื้นที่นั้น แกนในเกมกำหนด east = +X, north = -Z, up = +Y มี cityOrigin และ projectScale ที่ version ไว้

ค่าเริ่มต้นโครงการ: 1 เมตรจริง = 1 เมตรในเมืองฐาน และใช้ 1 stud = 0.28 เมตรตาม [Roblox units](https://create.roblox.com/docs/physics/units) ดังนั้น `studs = meters / 0.28` การแปลงต้องอยู่ที่ boundary เดียว ไม่ให้แต่ละระบบคิดหน่วยเอง

พื้นที่ 300 เมตรจึงกว้างประมาณ 1,071 studs ต่อด้านตามค่านี้ เป็นเพียงการคำนวณหน่วย ไม่ได้ยืนยันว่าทางเดินจริงทุกช่วงวัดแม่นแล้ว

ทำ control points ที่ตรวจได้อย่างน้อย 5 จุด เช่น มุมกำแพง จุดตัด และแนวคูน้ำ ตรวจ overlay ภายในเครื่องมือที่มีสิทธิ์ใช้ เป้าคลาดเคลื่อนเริ่มต้น 3 เมตรสำหรับตำแหน่งหลักเป็นเกณฑ์โครงการ ไม่ใช่ความแม่นที่รับรองจาก OSM หากแหล่งต้นทางแย่กว่านั้นให้บันทึกและหาข้อมูลเพิ่ม

เมืองใหม่ต้องมี origin และการฉายพิกัดของตัวเอง ไม่ใช้ค่าระยะต่อองศาของเชียงใหม่ไปทั่วโลก วางแต่ละ Place ใกล้จุดกำเนิดของมัน ลดปัญหาพิกัดใหญ่มากเมื่อขยายเมือง

## 7. Metadata ที่ต้องติดกับพื้นที่

```yaml
cityId: city.th.chiangmai
districtId: district.chiangmai.thaphae
cellId: cell.cm.tp.0001
sourceFeatureIds: [] # ใส่ IDs จริงเมื่อ import
geometryStatus: mapped # mapped | surveyed | estimated | fictional
sourceSnapshotId: pending
originVersion: 1
gameplayLayer: base # base | encounter | echo
rightsStatus: pending-review
```

ตัวอย่างยังไม่ใช่ข้อมูลสถานที่ที่ตรวจแล้ว `pending` ต้องไม่ผ่าน stage publish แยกสถานะความแม่นจากสิทธิ์ใช้งาน เพราะรูปทรงแม่นไม่ได้แปลว่าใช้ asset ได้ถูกสิทธิ์

## 8. รายละเอียดที่คุ้มทำก่อน

ลำดับแรกคือผิวถนนและทางเดินที่ไม่ซ้อนกระพริบ ขอบคูน้ำ รูปประตู อิฐ ต้นไม้ระดับสายตา เงา และช่องเดินจริง ต่อมาคืออาคารที่เห็นใกล้บริเวณเล่น ส่วนภายในบ้านทุกหลัง ยอดตึกที่ไม่เห็น และพร็อพซ้ำหลายพันชิ้นรอหลังพิสูจน์ประสิทธิภาพ

ถนนเชื่อมกันต้องไม่มีพื้นซ้อนระดับเดียวกัน เก็บ collision ให้เรียบ ใช้รูปทรงหยาบแยกจาก mesh ภาพ ซอยตันต้องมีสัญญาณให้เห็น ไม่ให้ผู้เล่นติดมุมระหว่างเสาและป้าย

เริ่มแบบไม่มีการจราจรสมจริงหรือ NPC คนเดินเต็มเมือง เพิ่มเมื่อมีงบ CPU/ภาพและเหตุผลด้านการเล่น

## 9. Streaming และการแบ่งเซลล์

Roblox มี instance streaming โหลดและถอดเนื้อหาใกล้ตัวผู้เล่น; สิ่งที่อยู่ใน ReplicatedStorage ไม่ได้ใช้ streaming แบบ Workspace ตาม [Instance streaming](https://create.roblox.com/docs/workspace/streaming)

ข้อเสนอของโครงการคือแบ่งเมืองเป็นเซลล์งานราว 100 เมตรเพื่อผลิตและตรวจคุณภาพ ไม่เขียนระบบโหลดทุกชิ้นเองแข่งกับ engine ตั้งชื่อและ metadata ให้ค้นได้ รัศมีโหลดจริงต้องวัดจากเครื่องเป้าหมาย ไม่ถือว่าขนาดเซลล์เท่ากับรัศมี streaming

client ต้องทนกรณีวัตถุยังไม่โหลดหรือถูกถอดออก ไม่รอ object โดยไม่มี timeout UI ใช้ ID/ข้อมูลสถานะจากเซิร์ฟเวอร์แทนผูกชีวิตเควสต์กับ instance ฝั่ง client

## 10. ขยายเมืองและโลก

ลำดับเสนอ: ท่าแพเล็ก → เชื่อมถนนหลักบางช่วง → เขตคูเมืองที่ผ่านเกณฑ์ → เมืองที่สองเพื่อพิสูจน์ pipeline → เครือข่ายเมือง อย่าเริ่มปั้นทุกจังหวัดก่อนรู้ต้นทุนต่อหนึ่งเซลล์

แพ็กเมืองใหม่ต้องมี manifest, origin, source/rights, modular kit, landmark, จุดพัก, ขอบเขตห้ามต่อสู้, event templates, ภาษา และชุดทดสอบ เสนอใช้ Experience เดียวหลาย Place เมื่อจำเป็น ไม่สร้างเซิร์ฟเวอร์เมืองทุกประเทศขึ้นตลอดเวลา

การเดินทางข้าม Place ผ่าน TeleportService ต้องทดสอบในเกมที่ publish และ Roblox client ตาม [Teleport between places](https://create.roblox.com/docs/projects/teleport) จึงเป็น milestone แยกจากการทดสอบใน Studio

## 11. เกณฑ์รับงานเมือง

- แนวถนนหลักและ control points ตรวจเทียบและบันทึกข้อคลาดเคลื่อน
- เดินจากจุดเกิดถึงทุกเป้าโดยไม่ทะลุพื้น ติดมุม หรือข้ามคูน้ำผิดจุด
- หมุน/ซูมใกล้และไกลแล้วไม่พบผิวซ้อนกระพริบที่ทดสอบ
- แยก real geometry / estimated facade / fictional echo ได้จาก metadata
- UI ปกติไม่มีป้ายชื่อสถานที่หรือหมุดลอยเต็มฉาก โหมดช่วยนำทางเปิดตามต้องการ
- มี attribution และประวัติแหล่งข้อมูลที่เข้าถึงได้
- streaming ไม่ทำให้ตัวละครตกพื้น เควสต์หาย หรือบอสค้าง
